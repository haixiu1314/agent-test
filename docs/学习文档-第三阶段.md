# 第三阶段学习文档：从一条用例到可追溯结果

更新日期：2026-11-04。所有源文件位于 `E:\Project-xhb\ai-test` 下。建议先按照《操作文档-第三阶段》跑一次协议回显实验，再阅读本篇。

## 1. 三个名词先分清

**用例**描述“输入什么、希望发生什么、怎样判定”。**任务**描述“用哪个 Agent 版本执行哪组用例，以及并发、超时、重试配置”。**结果**记录“一条用例实际上发生了什么”。一个任务可以有多个结果，每个结果又可以有多个评估器结论。

例如，两条用例分别要求回答含“你好”和含“不可能出现的内容”。任务执行完后，一条通过、一条失败，任务状态仍为已完成。完成与通过是两种不同信息。

## 2. 整条调用链

```text
浏览器 Tasks.vue
  → POST /api/v1/test-tasks（创建快照与待执行结果）
  → POST /api/v1/test-tasks/{id}/start（启动调度）
  → TaskManager.run（限制并发，领取待执行用例）
  → execute_case（调用适配器，处理超时/重试）
  → HTTP / 受控本地 Agent
  → evaluate（逐一调用规则、语义或专业评估器）
  → MySQL 保存结果、评估依据和可观测事件
  → 浏览器查询进度和结果
```

浏览器不直接请求外部 Agent，也不接触解密后的 API Key。后端负责鉴权、权限检查、配置解密和持久化。

## 3. 为什么创建任务时要拍快照

假设今天使用 Agent v1 和套件 r3 发现错误，明天把 Agent 改为 v2、修改了一条用例。如果任务只保存“当前 Agent ID”，以后打开历史就无法确认当时用了什么配置。

`backend/app/services/tasks.py` 的 `create_task` 读取 `AgentVersion` 和 `TestSuiteVersion`，把所选版本、用例内容及模型配置固定下来。密钥单独加密。重跑也复制原任务快照，所以同一次实验的输入有据可查。

快照不是数据库备份，也不冻结远端服务本身。远端地址对应的程序若已经换版，平台不能替你保证它仍是旧程序。严格回归需要给各版本保留独立地址或可验证版本标识。

## 4. MySQL 存什么

| 表 | 本阶段用途 |
| --- | --- |
| test_tasks | 任务配置、版本快照、状态、开始与结束时间 |
| test_results | 每条用例状态、响应时间、尝试次数、实际用量、加密载荷 |
| evaluation_details | 每个评估器的状态、分数与依据 |
| trace_events | 输入、输出、重试、异常、目标提供的工具事件 |
| security_findings | 安全类型用例的保守风险记录；不代表完整安全模块已验收 |

类位于 `backend/app/models/platform.py`，实际迁移位于 `backend/migrations/versions/0005_platform.py`。迁移文件使用固定的建表指令，避免以后修改模型时意外改变旧迁移。后续阶段草稿模型存在，但本次只新增上述五张表。

`test_results` 对“任务 ID + 用例 ID”设置唯一约束，避免同一任务重复创建结果。外键使任务、Agent 和套件保持关联，因此有关联历史时会拒绝删除源记录。

## 5. 并发不是无限开线程

`TaskManager` 使用 Python `asyncio`：等待网络响应时允许处理其他用例。`Semaphore` 像有固定数量工位的实验室，并发数为 2，就最多允许两条目标调用同时进入。

`schedule` 限制进程最多三个活跃任务；`run` 管理一个任务；`execute_case` 处理一条用例。数据库状态用于持久化，内存中的 running 字典只表示本进程正在运行的协程。

目前是单进程执行器。不要启动多个 Uvicorn worker，共享数据库并不自动让多个执行器正确协作。多进程或分布式执行需要额外的任务队列、租约和心跳设计。

## 6. 暂停、取消、超时、重试分别解决什么

暂停将任务改为 `pause_requested`，领取新用例前检查状态，在途用例完成后改为 `paused`。继续时只领取 `pending`。

取消将运行任务改为 `cancel_requested`，在途用例结束后把剩余用例标记 `cancelled`。这样已经收到的结果不会丢失，但也意味着取消不会立刻停止远端业务动作。

超时限制一次调用等待多久；重试限制出错后最多再调用几次。重试次数为 1 时，最多尝试两次。规则失败通常是业务结论，不会因为判定失败就自动重新请求 Agent；“重跑未通过”会创建独立任务。

`backend/app/main.py` 的 lifespan 是应用启动与关闭钩子。启动时把遗留运行任务标为中断、运行结果标为异常。继续任务时，只重新执行中断和未执行的条目。远端动作可能已执行，因此恢复也需要考虑业务幂等。

## 7. 混合评估怎样工作

`backend/app/services/evaluation.py` 的 `evaluate` 读取用例的 `rules.evaluators`，逐个执行并保存结论：

- `rules`：检查关键词、禁止词、JSON 顶层字段、状态码、响应时间和尝试次数，适合确定条件。
- `tool_trace`：检查实际工具名称、参数与成功结果；回答是否使用工具结果需要语义评估。只有关键词不能证明调用过工具。
- `llm_judge`：把用例、实际回答和证据交给模型，验证结构化结论。模型本身也可能误判，结果需要审阅。
- `conversation`：要求历史对话存在，再判断上下文连贯性。
- `deepeval`：调用专业库的 Answer Relevancy；有实际检索上下文时再加入 Faithfulness。

`aggregate` 汇总时，失败优先，其次异常，缺配置或证据则待判定，只有全部通过才通过。一个评估器异常不会抹去其他已经完成的评估依据。

评分不是随意生成的百分比。缺模型没有分数，不会自动给满分。DeepEval 的相关性指标主要衡量“是否围绕问题”，语义正确性仍需要相应 rubric 与 Judge；不能把相关性直接等同于事实正确。

专业集成位于 `backend/app/integrations/professional.py`：`JudgeModel` 让 DeepEval 使用项目配置；`deep_eval` 构造 `LLMTestCase` 并实际运行指标算法。当前已用明确的模型替身验证契约，真实模型调用仍未验收。

RAGAS 的完整能力属于第四阶段，本阶段不把草稿或不可用分支当成已交付功能。

## 8. 证据与数据安全

`AgentResponse` 是适配器统一输出，位于 `backend/app/adapters/base.py`。它携带回答、HTTP 状态、尝试次数、可观测事件、Token 和实际上下文。

`HttpAgentAdapter` 使用字段映射适配不同 API。`EnterpriseAdapter` 调用第二阶段企业助手。`protocol_echo` 是非 AI 协议工具，用来排查平台流程。

没有工具事件，`events_observable` 就是 false；没有 Token，usage 就是空对象。平台不根据最终回答编造工具调用、Token 或模型内部思维链。

配置密钥、实际输入输出和事件载荷使用 SecretVault 加密。鉴权后才解密返回所属项目用户。版本快照中的用例内容和评估依据等业务元数据仍存于关系字段中，不能把这理解为数据库全盘加密；数据库备份仍应保护。

## 10. 怎样调试和继续学习

先只用一条规则用例、并发设为 1，记录任务 ID。打开 API 文档，查询 progress、results，再查看 trace 的输入和输出。出现异常时用请求编号查 `.local/backend.log`，不要把密钥写进打印语句。

随后按顺序实验：把必须包含词改错，观察失败；选择未配置的 Judge，观察待判定；把超时调小，观察异常与尝试次数；创建多条慢请求，观察暂停后剩余 pending；执行失败重跑，观察新旧任务 ID 和版本。

快速测试用 SQLite 替代数据库，可验证业务分支，但无法证明 MySQL 行为。真实 MySQL、真实 HTTP、浏览器、真实模型是不同层面的证据，必须分别记录。这也是本阶段验收报告不把所有“通过数量”简单加总的原因。
